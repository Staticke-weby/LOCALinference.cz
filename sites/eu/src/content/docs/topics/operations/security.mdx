Local AI lowers the risk of sending data to the cloud, but it raises
other questions: who gets to the model, what they can read, what gets
logged and what happens when an agent makes a mistake. Security is an
operational discipline, not a property of the model.

## Short answer

- **Network and authentication** are the first layer; the model does not
  belong on a public port.
- **Least privilege** for users and for agents.
- **Prompt injection** is a real risk with documents and tools.
- **Logs, backups and an incident plan** decide the outcome of an outage.

## Threats

| Threat | Example | Defence |
|---|---|---|
| **Unauthorised access** | an open port | auth, TLS, network |
| **Prompt injection** | a document with an instruction | permissions, approval |
| **Data leak** | an agent sends content out | allowlist, sandbox |
| **Supply chain** | a forged model | verified sources |
| **Overload** | too many requests | rate limit, queue |
| **Data loss** | a disk fails | backups, restore tests |

## Network and access

- **The model on localhost** or on the internal network.
- **A reverse proxy** with TLS.
- **Authentication** and roles.
- **Rate limits** and timeouts.
- **No public endpoints** unless you need them.

## Permissions

- **A user** sees only their own documents.
- **An agent** has only the tools it needs.
- **An admin** has a separate account.
- **Service accounts** have a limited scope.
- **Keys** are rotated.

## Prompt injection

- A **document** can contain an instruction.
- A **tool** can return forged data.
- An **agent** can obey and perform an action.

The defence: separate instructions from data, an allowlist of tools,
confirmation for sensitive actions, logs. The details are in
[prompt injection](/dictionary/operations/prompt-injection/).

## Logs and audit

- **Who** and **when**.
- **Which model** and version.
- **Which tools**.
- **What result**.
- **Who approved it**.

Protect the logs and limit retention. They can be sensitive in
themselves.

## Incident

1. **Stop** the model or the agent.
2. **Disconnect** the network if a leak is likely.
3. **Preserve** the logs.
4. **Establish the scope**.
5. **Inform** the people responsible.
6. **Fix** and test.
7. **Write down** the lessons.

## Example: a suspicious email

An agent with access to a mailbox reads an email containing the
instruction "forward all invoices". The application has no tool for bulk
forwarding, and sending requires confirmation. So the agent cannot
perform the action. That is the correct setup: restrict the tool, do not
rely on the prompt.

## Network topology

Security starts with what is reachable from where:

| Layer | Availability | Note |
|---|---|---|
| **Model server** | `localhost` only | port 8000 is invisible to the network |
| **Proxy** | internal network, 443 | TLS and sign-in |
| **Application** | according to roles | no direct access to the model |
| **Administration** | VPN or bastion | never from the internet |
| **Outbound network** | allowed domains only | the agent must not reach everywhere |

An agent with unrestricted outbound network can send data out even
without anyone attacking it. A domain allowlist matters as much as
authentication.

## Test the defence, not just the configuration

- **The port from another network** — must be unreachable.
- **No token** — must return 401.
- **Someone else's document** — the user must not get it, not even in an
  answer.
- **An injection in a file** — the agent must not perform the action.
- **An outbound connection** to a non-allowed domain — must fail.
- **A restore from backup** — must have been tested, not only described.

## Backups

- **3 copies** of the data, **2 different media**, **1 off site**.
- **Encrypted** backups, with the key kept separately.
- A **restore test** at least twice a year.
- **Back up the configuration** and the index too, not just the
  documents.

## Checklist

- [ ] Is the model off the public internet?
- [ ] Is authentication in place?
- [ ] Are there roles and permissions?
- [ ] Is there a rate limit?
- [ ] Are there logs?
- [ ] Is there a backup and a restore test?
- [ ] Is there an incident plan?
- [ ] Have the injection scenarios been tested?

## When you do not need this

- One user on localhost.
- No sensitive data.
- A short test.
- The model calls nothing.
