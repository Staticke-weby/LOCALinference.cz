Most problems with local AI have four causes: the model did not fit, the
engine does not see the GPU, the machine is overheating, or the context
is set up wrong. Before you start changing the model, find out which of
them it is. The tables below go from the most common to the rarest.

## Short answer

- **Check the GPU first**, not the model: `nvidia-smi`, `rocminfo` or
  `system_profiler`.
- **Look for `cuda`, `rocm` or `metal` in the engine log.** When they
  are missing, the computation is running on the CPU.
- **Slow running after a few minutes** is usually
  [throttling](/dictionary/operations/throttling/), not a weak model.
- **Poor quality** is usually quantization, sampling temperature or a
  wrong chat template, not a "stupid model".

## First: is the model running on the GPU?

| Platform | Command | What to look for |
|---|---|---|
| NVIDIA (DGX, RTX) | `nvidia-smi` | card name, driver, MiB in use |
| AMD (Strix Halo) | `rocminfo` | an agent with `gfx1151` |
| Apple | `system_profiler SPDisplaysDataType` | the chip and its core count |
| Engine | the start-up log | `cuda`, `rocm`, `metal` or `cpu` |

When the log says `cpu`, that is the most common cause of a "slow model".
The engine works, it just does not see the graphics card — usually
because of a wrong PyTorch build or a wrong driver.

## The model will not start

| Symptom | Cause | What to do |
|---|---|---|
| `out of memory` while loading | model plus KV cache did not fit | shorten the context, lower the quantization, smaller batch |
| `unknown model architecture` | an old engine | update [vLLM](/dictionary/software/vllm/) or [llama.cpp](/dictionary/software/llamacpp/) |
| `no kernel image is available` | torch does not match the architecture | reinstall torch for the right CUDA |
| `permission denied` on the model files | wrong permissions | fix the owner and the permissions |
| start-up takes many minutes | loading from a slow disk | keep the model on NVMe, not on a network drive |
| `CUDA error: driver too old` | the driver is older than the runtime | update the driver |

On the [DGX Spark](/devices/dgx-spark/) the official path is the NVIDIA
container; outside it, CUDA and driver versions can drift apart. Stick
to the [guide](/guides/dgx-spark/), not to blog recipes.

## It runs slowly

| Symptom | Cause | What to do |
|---|---|---|
| tens of seconds per token | computation on the CPU | check the GPU in the log |
| speed drops after a minute | [throttling](/dictionary/operations/throttling/) | improve cooling, lower the [power limit](/dictionary/operations/power-limit/) |
| the first answer takes long, then it is fast | prefill of a long prompt | shorten the context, enable [prefix caching](/dictionary/memory/prefix-caching/) and [flash attention](/dictionary/software/flash-attention/) |
| slower with every user | queue and KV cache | lower concurrency, watch [monitoring](/topics/operations/monitoring/) |
| much slower than the tables | a different quantization or context | compare the configuration, not just the model |

Before you start fixing anything, work out the
[roofline](/speed/roofline/): when a measured number exceeds the
theoretical ceiling, the measurement is wrong; when it sits far below
it, something other than memory is holding it back.

## It answers badly

| Symptom | Cause | What to do |
|---|---|---|
| it repeats itself, will not hold a format | sampling temperature | lower the temperature, cap max tokens |
| it does not understand the system prompt | chat template | use the template from the model card |
| it mixes languages | weak quantization | try a higher precision |
| it loses information in the middle | [context rot](/dictionary/memory/context-rot/) | shorter context, RAG |
| it invents tools | function calling | check the schema and the response format |

## By platform

| Platform | Typical problem | Where to look |
|---|---|---|
| Windows x64 | CPU fallback, driver | `nvidia-smi`, the ComfyUI log |
| Windows on Arm | a missing ARM64 wheel | build from source, or skip the node |
| DGX OS | CUDA version outside the container | the official NVIDIA container |
| Strix Halo | ROCm and `gfx1151` | `rocminfo`, [ROCm](/dictionary/software/rocm/) |
| macOS | MPS versus CPU | `mlx-lm`, the engine log |

On Windows on Arm the problems show up mainly with custom ComfyUI nodes:
some packages have no ARM64 wheel and the install ends with an error. The
[Windows recipe](/generation/recipes/windows/) lists the specific
packages that NVIDIA names.

On Strix Halo the most common cause is the combination of driver and
ROCm version. When `rocminfo` sees the card but the engine does not, the
problem is in the runtime, not in the hardware.

## What to send to support

When the problem is not solved, send three things instead of "it does not
work":

1. **The symptom** — the exact message or number, not an impression.
2. **The environment** — device, OS, engine and driver versions.
3. **The configuration** — model, quantization, context, batch, the
   command.

Without these the problem cannot be reproduced and the answer will be a
guess.

## Where the limit is

- **Not every problem is in the model.** Most are in the configuration.
- **An update can make things worse.** Pin the versions that work.
- **Throttling is not visible from one number.** Watch the trend.
- **Community recipes age.** Check the date and the version.
